## 2. Что показал анализ теста

Изучены `api.mjs`, `server.mjs`, `cli.mjs`, `index.html` и README. Секретные env-файлы и содержимое файла состояния записи не читались. Повторные запросы и создание записи в этом анализе не выполнялись. Успех теста зафиксирован со слов пользователя; отдельного обезличенного отчёта с фактическими ответами среди изученных файлов нет.

Полезная проверенная реализацией основа:

- Node выполняет запросы к `https://api.alteg.io/api/v1`; браузер обращается к локальному серверу.
- Заголовки: Partner Bearer Token, `Accept: application/vnd.api.v2+json`, JSON для тела.
- Каталог читается через `book_services` с `without_seances=1`; есть команды сотрудников, дат, окон, проверки, создания и чтения записи.
- Есть таймаут 15 секунд, запрет HTTP redirect, чтение JSON/пустого ответа, ненулевой exit code CLI при неудаче.
- Файл состояния создаётся эксклюзивно до POST и не даёт повторить попытку после неопределённого результата. Это хорошая защита для одного локального теста.
- README фиксирует наблюдение: для тестируемого филиала при создании потребовался `email`. В будущем это необходимо учитывать в контракте букинга; не считать email обязательным для всех филиалов только по этому наблюдению.

Что нельзя переносить в production как есть:

| Наблюдение | Следствие для внедрения |
|---|---|
| Услуга, сотрудник, datetime и имя тестового клиента зашиты в `api.mjs` | Эти значения не являются настройками сайта; нельзя копировать их в компоненты и бизнес-логику |
| Локальный API возвращает практически сырой ответ Altegio | Публичный API сайта должен выдавать только разрешённые нормализованные поля |
| `redact()` скрывает токены/hash и отдельные значения, но не маскирует телефон и все клиентские поля | Нельзя публиковать диагностику теста или использовать эту функцию как универсальную очистку персональных данных |
| `verify` сравнивает ID, сотрудника, наличие выбранной услуги, время и `deleted`; не проверяет личность клиента и точное равенство состава услуг | Успех smoke-проверки не доказывает все будущие критерии приёмки букинга |
| Один файл попытки на всю папку, без полноценного жизненного цикла запроса | Это не production-идемпотентность, не БД, не очередь и не защита между экземплярами приложения |
| `check` и `book` запускаются отдельно | Защиту от гонки при создании ещё предстоит реализовать; проверка окна не резервирует его |
| Чтение по hash пробуется с Partner Token | Даже успешный конкретный тест не определяет срок жизни hash и модель авторизации кабинета |

Повторно использовать нужно знание протокола и обезличенные формы данных, а не импортировать `tools/altegio-smoke/api.mjs` в сайт. Сам инструмент оставить локальной диагностикой, не выставлять его маршруты публично.

## 3. Принятая структура

```text
Server Component ──────────────┐
                              ▼
                       server/catalog/*
                              │
Browser → /api/catalog/* ──────┘
                              ▼
                       server/altegio/* → Altegio
```

Серверный компонент вызывает серверную функцию напрямую. Он не делает HTTP-запрос к собственному `/api`. Клиентские компоненты при необходимости используют Route Handler того же origin. Токен не пересекает серверную границу. Это соответствует [рекомендации Next.js для Server Components](https://github.com/vercel/next.js/blob/v16.4.5/docs/01-app/02-guides/backend-for-frontend.mdx).

План структуры. Фактические пути этапа 1 перечислены в разделе 7.

```text
src/
  server/
    config.ts                    # server-only, проверка env при использовании
    altegio/
      client.ts                  # HTTP, auth, timeout, безопасные ошибки
      errors.ts                  # ошибки upstream без секретных payload
      types.ts                   # только реально используемые формы ответа
      services.ts                # чтение каталога Online Booking
    catalog/
      services.ts                # проверка, нормализация, кеш публичных данных
  lib/
    contracts/catalog.ts         # DTO без server-only импортов
  app/api/catalog/services/
    route.ts                     # GET; тонкий публичный адаптер
  components/sections/
    HomeServices.tsx              # получение и вывод секции главной
  content/
    home-services.ts             # привязка утверждённых иллюстраций по ID
messages/{ru,en}.json            # тексты карточек главной по ID
```

Не создавать заранее пустые booking/account/webhook-модули. Добавлять их по мере реализации соответствующего этапа. Не нужен универсальный прокси, принимающий URL, произвольный метод или credentials от браузера.

### Минимальный контракт между первым и вторым чатом

- Серверная функция: `getCatalogServices(locale)` из `src/server/catalog/services.ts`.
- Публичный метод: `GET /api/catalog/services?locale=ru|en`, без произвольного филиала из браузера. Без locale использовать `en`; неподдерживаемый locale — 400.
- Единый DTO в `src/lib/contracts/catalog.ts`; после этапа 1 фактические имена и пример ответа записать сюда.
- Успех: `{ data: { services, categories }, meta: { source: 'altegio', locale } }`.
- Поля услуги: `id`, `title`, `description: string|null`, `categoryId: number|null`, `priceMin: number|null`, `priceMax: number|null`, `currency: string|null`, `durationMin: number|null`, `imageUrl: string|null`. Категория: `id`, `title`.
- Описание — безопасный plain text. Не выдавать сырой HTML, внутренние комментарии и поля клиентов. Отсутствие значения — `null`, а не придуманная цена/длительность.
- Порядок каталога сохранять из нормализованного ответа. Редакционный порядок главной определяется отдельно; в DTO пока не требуются выдуманные slug и `hasCms`.
- `locale` в meta означает запрошенный язык интерфейса, не обещание, что исходное название уже переведено. Если переводов нет — оригинальное название, без машинного перевода при каждом запросе.
- Ошибка: `{ error: { code, message, requestId? } }`, без тела upstream, токена, stack trace и полного URL чувствительных запросов. Коды и HTTP mapping должен зафиксировать этап 1.

Валюта и длительность требуют проверки на ответе конкретного филиала. `book_services` без сотрудника может не содержать длительность. Не делать N+1 запросов по сотрудникам для заполнения карточек. Не брать AED и 100 минут из демо-каталога; при отсутствии валюты в ответе нужна проверенная серверная настройка филиала.

## 4. Почему этап 1 включает смену режима запуска

Для серверного общения с Altegio проект перешёл на Node.js runtime Next.js с `next build` и `next start`. Сохранены версия фреймворка и `cacheComponents: false`.

Переход изменил команды build/start/serve, проверки, предзагрузку шрифтов и заголовки. Перед выкладкой нужен Node Web Service либо другой хостинг серверного Next.js. [Варианты размещения Next.js](https://github.com/vercel/next.js/blob/v16.4.5/docs/01-app/01-getting-started/17-deploying.mdx).

Успешные публичные данные кешируются с ревалидацией через 14400 секунд. Сборка проходит без доступа к Altegio и без токена. При обращении к API отсутствие конфигурации даёт управляемую ошибку. Для доступности и записи действуют отдельные правила.

## 7. Передача результата между чатами

### Этап 1. Серверная основа

- [`src/server/config.ts`](../src/server/config.ts) проверяет серверное окружение при обращении. [`src/server/altegio/`](../src/server/altegio) содержит GET-транспорт, безопасные ошибки и запрос `book_services/{location_id}?without_seances=1`.
- [`src/server/catalog/services.ts`](../src/server/catalog/services.ts) проверяет и нормализует ответ. Server Components импортируют `getCatalogServices(locale: CatalogLocale): Promise<CatalogServicesResponse>` напрямую. [Route Handler](../src/app/api/catalog/services/route.ts) вызывает ту же функцию.
- [`src/lib/contracts/catalog.ts`](../src/lib/contracts/catalog.ts) содержит общий DTO. `GET /api/catalog/services?locale=ru|en` использует `en` по умолчанию. Дополнительные и повторные параметры отклоняются. `meta.locale` отражает запрошенную локаль. Названия передаются из CRM в исходном виде.
- В корневом игнорируемом `.env.local` используются `ALTEGIO_LOCATION_ID`, `ALTEGIO_PARTNER_TOKEN` и необязательная `ALTEGIO_CURRENCY`. Формат значений и запуск описаны в [CONFIG-DEPLOY.md](CONFIG-DEPLOY.md). Локальные команды — `npm run build`, затем `npm run start` или `npm run serve`. Для выкладки понадобится Node Web Service. Удалённый хостинг в рамках этапа не менялся.

Пример с синтетическими ID и ценой

```json
{
  "data": {
    "services": [
      {
        "id": 42,
        "title": "Massage",
        "description": null,
        "categoryId": 20,
        "priceMin": 0,
        "priceMax": 55,
        "currency": null,
        "durationMin": null,
        "imageUrl": null
      }
    ],
    "categories": [{ "id": 20, "title": "Massage" }]
  },
  "meta": { "source": "altegio", "locale": "en" }
}
```

Порядок сохраняется. Категории читаются из `category` с поддержкой `categories` из текстового описания API. Онлайн-публикацию определяет сам endpoint. Поле `active` не используется как дополнительный фильтр. Ноль сохраняется, скидка повторно не применяется. `durationMin` получается из положительного `seance_length` в секундах. `description` берётся из непустого текстового `comment` публичного `book_services`. Значения с HTML-разметкой пропускаются. `imageUrl` принимает абсолютные HTTPS-адреса без встроенных учётных данных. Валюта берётся из подтверждённой настройки филиала `ALTEGIO_CURRENCY`.

Ответ ошибки имеет вид `{ "error": { "code": "...", "message": "..." } }`.

| HTTP | Код | Условие |
|---|---|---|
| 400 | `INVALID_QUERY` | Значение локали, повторение или лишний параметр запроса |
| 503 | `CATALOG_UNAVAILABLE` | Конфигурация, ошибка соединения или upstream HTTP-ошибка, включая 401, 403, 5xx |
| 503 | `UPSTREAM_RATE_LIMITED` | Upstream 429. `Retry-After` нормализуется до 1–3600 секунд, по умолчанию 60 |
| 504 | `UPSTREAM_TIMEOUT` | Таймаут транспорта 10 секунд, включая чтение ответа |
| 502 | `UPSTREAM_INVALID_RESPONSE` | Пустое тело, невалидный JSON, неверный envelope или DTO, `success: false` |
| 500 | `INTERNAL_ERROR` | Непредвиденная внутренняя ошибка |

### Кеш и ISR для следующих этапов

[`cachePublicCatalog`](../src/server/catalog/cache.ts) хранит проверенный DTO в Next Data Cache при `cacheComponents: false`. Интервал — **14400 секунд**. Ключ учитывает ресурс, версию, филиал и локаль, для услуг ещё валюту. Метаданные локали добавляются после чтения кеша. Ответ API всегда использует `Cache-Control: no-store`. При холодном кеше ошибка видна потребителю. После истечения интервала запрос может получить последнее успешное значение во время обновления и при сбое, поэтому четырёхчасовой интервал не задаёт максимальный возраст ответа.

- Один процесс Next.js объединяет обращение к Altegio и запись результата для одного ключа. На холодном кеше запросы ждут общий результат. При наличии предыдущего DTO API отдаёт его сразу, пока идёт фоновое обновление. [Адаптер Data Cache](../src/server/catalog/next-data-cache.ts) использует внутренний интерфейс установленного Next.js 16.4.5. При обновлении Next.js повторите production-тест каталога. Переход с `unstable_cache` меняет внутренний ключ, поэтому первая загрузка после него будет холодной.
- После `429` процесс выдерживает нормализованный `Retry-After` для этого ключа. Пока идёт пауза, API отдаёт предыдущий каталог или, при его отсутствии, `503 UPSTREAM_RATE_LIMITED` с оставшимся числом секунд, округлённым вверх. Во время паузы обновление не запускается, время последней успешной записи сохраняется. Следующая серия запросов после паузы снова делит одну попытку. Активные загрузки и сроки пауз хранятся в памяти процесса и сбрасываются при перезапуске. Несколько процессов координируются независимо.
- Публичные профили сотрудников используют ту же политику со своим ключом. Свободные окна, ближайшие слоты, проверка доступности, букинг, кабинет и личные данные обходят этот кеш.
- Статически подходящие страницы услуг и команды используют ISR с литералом `export const revalidate = 14400`. #### Часть 5.1. Read-only API каталога и доступности

**Статус — реализована и проверена, 15.11.2026.**

| GET-маршрут | Параметры | Поля в `data` |
|---|---|---|
| [`/api/booking/staff`](../src/app/api/booking/staff/route.ts) | `serviceId`, `locale` | `serviceId`, `staff: [{ id, name }]` |
| [`/api/booking/dates`](../src/app/api/booking/dates/route.ts) | `serviceId`, `staffId`, `locale` | `serviceId`, `staffId`, `dates: string[]` в формате `YYYY-MM-DD` |
| [`/api/booking/times`](../src/app/api/booking/times/route.ts) | `serviceId`, `staffId`, `date`, `locale` | `serviceId`, `staffId`, `date`, `times: [{ datetime, time }]` |

- `locale` принимает `ru` или `en`, по умолчанию `en`. Услуга проверяется по публичному каталогу. Список назначенных специалистов берётся из `book_staff` с одним `service_ids[]` через существующий кеш каталога. Видимый специалист с `bookable: false` остаётся в списке назначений. Для дат и времени `staffId=0` означает «Любой специалист». Остальные ID проверяются по списку специалистов услуги.
- Даты берутся из `data.booking_dates` в `book_dates`, время — из `book_times/{location_id}/{team_member_id}/{date}`. Оба запроса используют один `service_ids[]` и выполняются заново. Сервер использует диапазон доступных дат, который возвращает Altegio. Время `HH:mm` рассчитано в `Asia/Dubai`, исходный `datetime` передаётся целиком, включая смещение. При выборе «Любой специалист» в ответе сохраняется `staffId=0`.
- Ответы используют `Cache-Control: no-store`. Пустая доступность возвращает `200` и пустой массив. Неверные параметры дают `400 INVALID_QUERY`, отсутствующая услуга или неподходящий специалист — `404 SERVICE_NOT_FOUND` или `404 STAFF_NOT_FOUND`. Сбой Altegio возвращает `503`, невалидный ответ — `502`, таймаут — `504`, ограничение частоты — `429`. Валидный `Retry-After` из Altegio передаётся клиенту.
- Production-проверка `npm run test:booking-availability` подтвердила фильтры и параметры для разных услуг и сотрудников, работу `staffId=0`, пустые даты и окна, смену месяца, свежие ответы на одинаковые запросы, сохранение исходного смещения и время Дубая при другом часовом поясе процесса. Также проверены `429` с числовым и календарным `Retry-After`, `503`, невалидный ответ, таймаут и повтор после сбоя.
- GET-сверка через уже запущенное приложение подтвердила по одному назначенному специалисту для услуг `13982355` и `13983057`. В обоих режимах каждая услуга вернула 16 дат с 15 по 30 ноября 2026 года. На 30 ноября — 22 и 23 окна соответственно, с исходным смещением `+04:00`. На 1 декабря оба режима вернули пустой список для обеих услуг. Это наблюдаемый диапазон доступности проверенных услуг. Настройка горизонта в админке филиала не подтверждена.
