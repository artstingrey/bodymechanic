## PR-001. Заменить внутренний адаптер кеша Next.js документированным механизмом

**Статус:** отложено до после релиза по решению пользователя.

**Добавлено:** 14.11.2026.

**Тип:** технический долг, снижение зависимости от внутреннего устройства фреймворка.

### Контекст

Сайт The Body Mechanic и серверная интеграция Altegio находятся в одном Next.js-проекте. Первый этап внедрения подготовил серверный клиент, нормализованный каталог и `GET /api/catalog/services`. На момент постановки задачи используется Next.js 16.4.5 с `cacheComponents: false`.

Редко изменяющиеся публичные данные — услуги, категории и в дальнейшем профили сотрудников — кешируются с интервалом ревалидации **14400 секунд (4 часа)**. Свободные окна, ближайшее время сотрудника, создание записи, кабинет и персональные данные под это правило не подпадают.

При ревью первого этапа подтверждённых блокирующих дефектов не найдено. Проверки API и кеша прошли. Однако для работы кеша используется собственный адаптер, обращающийся к внутренним модулям Next.js. Это риск сопровождения и обновления зависимостей, а не установленная поломка сайта.

К моменту выполнения этой задачи могут быть подключены новые разделы. Исполнитель должен сначала проверить актуальный код и всех потребителей кеша, а не исходить из того, что каталог используется только HTTP API.

### Что именно требуется заменить

В `next-data-cache.ts` используются импорты из `next/dist/server/...`, в частности `workAsyncStorage`, `workUnitAsyncStorage` и `willConsumerServerCache`. Адаптер читает внутренний `incrementalCache`, самостоятельно формирует записи вида `FETCH` и меняет служебный контекст рендеринга.

Эти интерфейсы принадлежат реализации Next.js. Их расположение, типы и поведение могут измениться при обновлении фреймворка. Они не являются API Altegio и не нужны непосредственно для получения услуг.

По истории Git исходная версия `65d587d` использовала `unstable_cache` из `next/cache`. В `856283d` появился собственный адаптер для координации всего цикла чтения, обновления и записи. Историю можно использовать для понимания, но простой откат потеряет добавленное поведение.

**Цель:** убрать прямую зависимость прикладного кеша от внутренних модулей Next.js, сохранив полезное внешнее поведение и действующий контракт сайта.

### Предпочтительное направление

1. Изучить актуальную версию Next.js, AGENTS.md, локальные руководства в `node_modules/next/dist/docs/` и документацию через Context7.
2. Для сохранённого `cacheComponents: false` в первую очередь рассмотреть документированный `unstable_cache` из `next/cache`: кешировать проверенный нормализованный результат с `revalidate: 14400`.
3. Объединение параллельных обращений к Altegio и выдерживание `Retry-After` оставить отдельной серверной логикой там, где это действительно необходимо. Не считать, что одна обёртка кеша автоматически гарантирует нужное поведение при конкуренции.
4. Если к этому времени проект уже перешёл на Cache Components, рассмотреть `use cache` и `cacheLife`. Самостоятельно включать Cache Components или обновлять Next.js ради этой задачи не нужно: это отдельное архитектурное изменение.
5. После замены удалить ненужный внутренний адаптер и обновить документацию передачи.

`unstable_cache` — документированный интерфейс приложения, несмотря на название. Next.js описывает и его использование, и переход на `use cache`. Состояние документации необходимо перепроверить на момент реализации: [справочник](https://github.com/vercel/next.js/blob/v16.4.5/docs/01-app/03-api-reference/04-functions/unstable_cache.mdx), [миграция на Cache Components](https://github.com/vercel/next.js/blob/v16.4.5/docs/01-app/02-guides/migrating-to-cache-components.mdx).

### Поведение, которое необходимо сохранить

- Общий серверный источник для Route Handler и Server Components; серверный компонент не обращается по HTTP к собственному API.
- Стабильные сигнатуры и DTO для потребителей, прежде всего `getCatalogServices(locale)` и HTTP GET. При наличии других потребителей сохранить и их контракты.
- Интервал 14400 секунд для публичного каталога. Это ревалидация по запросу, а не обязательный cron каждые четыре часа и не гарантия максимального возраста данных при сбоях.
- Ключи различают филиал и параметры, реально влияющие на результат. Общий кеш RU/EN допустим, пока исходные данные одинаковы и локализация добавляется после загрузки; если появились разные переводы upstream, учесть локаль в ключе.
- Проверка ответа до сохранения: ошибка, `success: false` или неверная схема не превращаются в успешный пустой каталог. Настоящий пустой каталог остаётся корректным результатом.
- При холодном кеше одновременные одинаковые обращения в одном процессе не создают серию одинаковых запросов к Altegio.
- При обновлении устаревших данных сохраняется защита от параллельного обращения к upstream.
- Если предыдущие успешные данные есть, сбой обновления не уничтожает их. Если данных нет — вызывающий получает предусмотренную ошибку.
- После 429 выдерживается `Retry-After`: при наличии каталога можно вернуть предыдущие данные, без него — предусмотренный 503. Ошибка не должна продлевать срок свежести старых данных как успешное обновление.
- Кеш каталога не распространяется на доступность, букинг и личные данные. Не добавлять общий автоматический retry для POST.
- Серверные токены и исходные диагностические ответы не попадают на клиент или в логи.
- Сборка не начинает требовать доступную CRM или её секреты из-за замены кеша.

Текущая координация одновременных загрузок и пауз действует в пределах одного процесса. Распределённые блокировки, Redis и новая БД не входят в эту задачу, если нет отдельного требования масштабирования.

### Проверки и критерии приёмки

1. На production-запуске проверить холодный и свежий кеш, пустой каталог, устаревание, успешное обновление, сбой и восстановление, серию одновременных запросов, 429 и повтор после паузы.
2. Проверить прямой вызов сервиса из Server Component, а не только Route Handler.
3. Проверить реальную ISR-страницу: исходную генерацию, обновление после истечения интервала, ошибку при обновлении и последующее восстановление. Отдельно проверить динамическую страницу, использующую тот же кеш данных, если такой потребитель есть.
4. Для моделирования времени использовать контролируемый тестовый механизм; не ждать четыре часа и не менять production-интервал ради теста.
5. Адаптировать `check-catalog.mjs`: сейчас часть проверок зависит от файлов `.next/cache/fetch-cache`, их времени изменения и подсчёта внутренних записей. Не переносить эту зависимость в новую реализацию только ради прохождения старого теста. Основные критерии — ответы пользователю, число обращений к Altegio, сроки обновления и отсутствие утечек.
6. Проверить отсутствие новых регрессий на всех уже подключённых страницах услуг и команды. Выполнить lint, typecheck, i18n, build и соответствующие серверные/браузерные тесты.
7. В изменённом прикладном слое не должно остаться импортов приватных кеш-модулей `next/dist/server/*` или ручного изменения внутренних store Next.js.

Тестировать на синтетическом upstream. Создавать записи, менять настройки филиала и читать клиентские карточки для этой задачи не требуется.

### Границы и отчёт исполнителя

Не переписывать UI, клиент Altegio и публичный DTO без обнаруженной необходимости. Не менять правила отмены, авторизацию и формы записи. Не использовать демонстрационный инструмент `tools/altegio-smoke` как production-зависимость. Не читать `bodymechanic-site-main.zip`.

В итоговом отчёте указать выбранный публичный механизм, удалённые зависимости от внутренних API, сохранённое поведение, фактические проверки ISR и ограничения. Изменение способа формирования ключа может вызвать однократное заполнение нового кеша после выкладки — это нужно отметить. Если полноценная замена требует изменения внешнего поведения, сначала сформулировать конкретный компромисс; не объявлять задачу выполненной, скрыто убрав защиту от повторных обращений или обработку 429.

После завершения обновить статус PR-001 здесь и описание кеша в общем плане внедрения. До этого задача остаётся отложенной и не должна автоматически включаться в работу над карточками.
