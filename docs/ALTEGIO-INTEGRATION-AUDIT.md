| Собственный API и его хранилище | Сессии, связь пользователя с клиентом Altegio, согласия, идемпотентность, собственные токены ссылок, заявки, очередь, статус обработки и дополнительная структура 3D-анкеты |

В Altegio есть возможности переводов и описаний, но наличие полного RU/EN-контента именно этого филиала не проверено. Нельзя считать, что CRM автоматически заменит редакционную часть сайта. Отдельная CMS полезна для редактирования сотрудниками; для первого запуска допустим согласованный управляемый источник файлов, если частота обновлений это позволяет.

Особенно важно:

- Отметки тела и заметки не являются стандартным каталогом Altegio. Правила рекомендаций утверждает студия; это не автоматически получаемая медицинская рекомендация.
- Шаблон [formatComment.ts](C:/next-js-projects/body-mechanic/src/lib/altegio/formatComment.ts) уже есть. Формировать комментарий нужно на сервере. Ограничение 1000 символов — требование проекта, а не подтверждённый здесь универсальный предел Altegio.
- Для повторного отображения зон следует хранить структурированные данные у себя либо в согласованных дополнительных полях записи. Обратный разбор свободного комментария ненадёжен.
- У записи, созданной администратором или по телефону, может не быть зон и метаданных сайта. Кабинет должен это корректно показывать.
- Заявка лендинга без времени и сотрудника — ещё не запись. Нужно определить, где она хранится, кто обрабатывает и как превращает её в запись. Наличие подходящего отдельного CRM-метода «лид» не подтверждено проведённым исследованием.

## 5. Статические страницы и актуальность

Оставить отдельный сервер и статический хостинг сайта возможно. Требуется выбрать стратегию обновления:

1. **Сохранить static export:** наличие окон и операции всегда получать через API во время работы пользователя; обновлять видимые цены/каталог; пересобирать сайт при изменении публикуемых страниц, переводов, slug, sitemap и SEO. При сборке нужен доступ к безопасной публичной проекции данных собственного API либо подготовленному снимку.
2. **Изменить способ размещения фронтенда:** если страницы и SEO должны обновляться без пересборки, рассмотреть серверный рендеринг/обновление кеша средствами Next.js. Отдельный API-сервер при этом остаётся отдельным.

Первый вариант — разумная начальная гипотеза для небольшого сайта, но не принятое решение. Нельзя оставить цены только в HTML старой сборки, а на подтверждении неожиданно использовать новые. Необходимо согласовать допустимое время устаревания, обновление перед подтверждением и UX изменения цены.

## 6. Что необходимо для доступа к Altegio

**Доступы:**

- `location_id` филиала; в старых названиях встречаются `company_id`/`salon_id`. `bookform_id` формы записи — отдельный идентификатор. При нескольких филиалах дополнительно определить область работы и модель выбора филиала.
- Partner Token из Developer Account Altegio Marketplace.
- Для бизнес-данных и управления — Business User Token с доступом к нужному филиалу и минимально необходимыми правами.
- Выделенный тестовый филиал либо согласованные тестовые услуга, сотрудник, время и телефон для будущей проверки создания записи.

Есть два документированных способа получить Business User Token: авторизация существующего бизнес-пользователя через `/api/v1/auth` или системный пользователь приложения. Во втором случае приложение должно быть установлено и активно в филиале; публикация в каталоге сама по себе не заменяет активацию. Тестовая установка черновика приложения предусмотрена документацией. [Получение ключей](https://developer.alteg.io/en/get-api-key), [установка приложения](https://developer.alteg.io/en/developers/marketplace-quickstart).

**Различать три сущности:** собственная сессия посетителя сайта, Business User Token интеграции и Booking User Token клиента Altegio. Они не взаимозаменяемы.

Типовые заголовки по документации:

```text
Accept: application/vnd.api.v2+json
Content-Type: application/json

Публичная онлайн-запись:
Authorization: Bearer <PARTNER_TOKEN>

Бизнес-методы:
Authorization: Bearer <PARTNER_TOKEN>, User <BUSINESS_USER_TOKEN>
```

Конкретный метод может иметь дополнительные требования. Media type `v2` не означает, что URL должен быть `/api/v2`: он используется и в описанных методах v1. Все секреты должны находиться на отдельном сервере или в локальном окружении будущего теста, не в `NEXT_PUBLIC_*`, браузере или репозитории.

**Настройка филиала:** опубликованные услуги и сотрудники; назначение услуг сотрудникам; реальные цены и длительности; рабочее расписание, перерывы и необходимые ресурсы; настройка онлайн-записи; часовой пояс и валюта; необходимость подтверждения телефона; уведомления; правила отмены/переноса; обязательная предоплата, если она используется.

Для Дубая интерфейс сейчас предполагает AED и `+04:00`; это нужно сверить с филиалом, а не подменять ответ API фиксированной строкой. Различные длительности/цены у сотрудников поддерживаются настройками Altegio. [Настройки услуг сотрудника](https://alteg.io/ru/support/knowledge-base/282688).

## 7. API, подходящий для сайта

На дату проверки Online Booking использует v1. В Business Management документация рекомендует v2 для новых интеграций, но отдельные нужные операции остаются в v1. V2 имеет другую структуру ответов, включая JSON:API; это не простая замена цифры в URL.

**V3 в полученной документации помечен `3.0.0-preview`, операции не объявлены работающими. Плановую дату из описания нельзя считать подтверждением релиза.** Для текущего проекта следует опираться на доступные v1/v2 и отдельно проверять фактическую доступность будущих версий. [Online Booking](https://developer.alteg.io/en/public/openapi), [Business v2](https://developer.alteg.io/en/b2b-v2/openapi), [статус v3](https://developer.alteg.io/en/b2b-v3/openapi).

Ниже пути Online Booking относительно `https://api.alteg.io/api/v1`:

| Действие | Метод | Важные особенности |
|---|---|---|
| Каталог онлайн-записи | `GET /book_services/{location_id}` | Фильтры по сотруднику/услугам/времени; `without_seances=1` позволяет получать каталог без требования свободных окон. Не смешивать «нет услуги» и «нет окна» |
| Сотрудники | `GET /book_staff/{location_id}` | Фильтры по услугам и времени; видимость, доступность, фото и рейтинг зависят от ответа и настроек |
| Ближайшие окна | `GET /book_staff_seances/{location_id}/{team_member_id}` | Нужен правильный контекст услуг, без демо-ID `101` |
| Доступные даты | `GET /book_dates/{location_id}` | Использовать даты, доступные для записи (`booking_dates`), не просто рабочие дни |
| Свободное время | `GET /book_times/{location_id}/{team_member_id}/{date}` | Учитывать услуги, datetime с часовым смещением и длительность; значения `seance_length`/`sum_length` — секунды |
| Проверка окна | `POST /book_check/{location_id}` | `appointments` с услугами, сотрудником и временем; успех описан как `201` без тела. Это не бронирование и не блокировка окна |
| SMS перед записью | `POST /book_code/{location_id}` | Настройка `phone_confirmation` филиала должна соответствовать поведению сайта |
| Создание | `POST /book_record/{location_id}` | `fullname`, `phone`, `appointments`; `code` при необходимом подтверждении. `staff_id: 0` — любой подходящий сотрудник |
| Получение записи по ID/hash | `GET /book_record/{location_id}/{record_id}/{record_hash}` | Проверить реальную модель доступа и срок использования hash; не выдавать её за гарантированную постоянную ссылку |
| Перенос онлайн-записи | `PUT /book_record/{location_id}/{record_id}` | Требования к пользовательской авторизации нужно подтвердить тестом, см. раздел 10 |
| Записи клиента | `GET /user/records` | Booking User, а не произвольный бизнес-токен; ограничивать филиалом |
| Отмена клиентской записи | `DELETE /user/records/{record_id}/{record_hash}` | Доступ по пользовательскому контексту/hash зависит от условий метода |
| Политика филиала | `GET /privacy_policy/{location_id}` | Проверить дополнительное соглашение филиала и необходимость его показа; не заменяет автоматически документы сайта |

При создании `appointments[].id` — идентификатор элемента запроса для сопоставления ответа; реальный номер созданной записи возвращается как `record_id`. Это разные поля. Нужно обработать все элементы ответа и не потерять частичные/многоэлементные сценарии, если они появятся в согласованном контракте.

Для кабинета с собственной авторизацией практичнее рассмотреть бизнес-методы через сервер: поиск клиента, затем `GET /api/v2/locations/{location_id}/appointments` с фильтром по `client_id`, пагинацией и связанными услугами/сотрудником. Поиск клиента в v1 `/locations/{location_id}/clients/search` сам по себе не доказывает личность: номер сначала подтверждается собственной авторизацией, найденные карточки проверяются на точное соответствие, дубликаты обрабатываются явно. Браузер не должен выбирать произвольный `client_id` и получать его историю.

Полный бизнес-каталог и сотрудники также доступны через `/api/v2/locations/{location_id}/services` и `/team_members`. Из него потребуется выделять публичную часть. Отзывы можно исследовать через бизнес-метод v1 `/comments/{location_id}`: публиковать только разрешённые поля и утверждённые отзывы, без контактных данных клиентов.

Для переноса через бизнес-API важно не спутать полный update записи с простым изменением datetime: изученный v1 PUT требует сохранения остальных актуальных полей. Сервер должен запрещать обход занятости и самостоятельно соблюдать правила клиентской отмены/переноса. Бизнес-права администратора не означают, что посетителю разрешены все те же действия. [Business v1](https://developer.alteg.io/en/b2b-v1/openapi), [Business v2](https://developer.alteg.io/en/b2b-v2/openapi).

## 8. Что согласовать с отдельным API-сервером

Имеющийся [BACKEND-CONTRACT](C:/next-js-projects/body-mechanic/docs/BACKEND-CONTRACT.md) — полезная основа, но перед реализацией необходимы дополнения:

1. **Адрес и транспорт.** Один origin с проксированием `/api` либо API-поддомен; настройки cookies, CORS, credentials и CSRF в соответствии с выбранной сессией. Отдельный сервер совместим с обоими вариантами.
2. **Общие настройки.** Филиал, валюта, часовой пояс, подтверждение телефона, ограничения действий, согласия и версия правил. Их нельзя хранить только в build-time флагах, расходящихся с Altegio.
3. **Каталог и содержимое.** Стабильные ID и slug, локаль/fallback, связь категорий, фото, длительность и стоимость при конкретном сотруднике; отдельное редакционное содержимое.
4. **Запись.** Возвращать фактические услуги, сотрудника, дату, длительность, стоимость/валюту, статус и безопасную ссылку. `RecordResult` только с ID/hash недостаточен для подтверждения, календаря и аналитики.
5. **Идемпотентность.** Ключ и контроль совпадения тела запроса; устойчивое хранение результата; поведение при занятом ключе и таймауте. `api_id` Altegio — внешний ID, а не документированная гарантия идемпотентности.
6. **Очередь.** Различать «запись подтверждена», «заявка принята на обработку» и «результат неизвестен». Для очереди нужен идентификатор запроса и способ узнать результат; нельзя обещать пользователю забронированное время до подтверждения.
7. **Авторизация.** Отправка/проверка кода, восстановление сессии и выход; серверные лимиты; CAPTCHA в нужных запросах. SMS для собственной сессии и код для Altegio book_record могут быть разными процессами.
8. **Кабинет.** Пагинация, несколько услуг, визиты вне сайта, отменённые записи/неявки, права `canCancel`/`canReschedule` и причины запрета. Прошедшее время не равнозначно факту посещения. Вместо локального фиксированного порога 24 часа — утверждённая серверная политика для каждого действия.
9. **Ссылка.** Отдельный endpoint одной записи, проверка владения или ограниченного токена до выдачи данных. Собственный срок действия/отзыв ссылки; не считать внутренний hash Altegio готовой политикой безопасности сайта.
10. **Согласия и анкета.** Явные поля и версии, серверная фиксация времени, согласованный срок хранения, запрет попадания контактов/заметок/секретов в логи и аналитику. Применять уже зафиксированные в проекте ограничения передачи отметок администраторам.
11. **Ошибки.** Машиночитаемые коды, ошибки полей, `retryAfter` для лимитов, истёкшая сессия/код, конфликт окна, отключённая услуга. Например, Altegio различает коды 432 (SMS), 433 (занято), 436 (нет сотрудника), 431 (телефон); всё это не должно отображаться как «ошибка сети».
12. **Заявки LP и интеграции маркетинга.** Хранение и обработка заявки отдельно от букинга, дедупликация `eventId`, доставка уведомлений и согласованный состав данных. Telegram/Meta/Google в текущем mock — только заготовки, не работающие подключения. Их секреты и фактическая отправка принадлежат серверу.

## 9. Обновления, webhooks и устойчивость

Документация Online Booking указывает лимиты 5 запросов/с и 200 запросов/мин на IP. Несколько посетителей через один API-сервер делят исходящий IP: нужны кеширование каталога, объединение одинаковых запросов, ограничение частоты и обработка 429. Доступность кешируется осторожно и повторно проверяется при создании. [Лимиты Online Booking](https://developer.alteg.io/en/public/openapi).

Для изменений услуг, категорий, сотрудников, расписания и записей предусмотрены webhooks. Сервер принимает их, обновляет/сбрасывает кеш и при необходимости инициирует пересборку публикуемых страниц. Изменение записи администратором в Altegio должно отражаться в кабинете.

У `POST /hooks_settings/{location_id}` есть важное эксплуатационное свойство: запрос заменяет полный список URL и набор событий филиала; пропущенные флаги отключаются. Перед изменением нужно прочитать настройки и сохранить подключения других интеграций. В рамках этого аудита настройки не менялись.

Доставка может повторяться и запаздывать; `X-Hook-Id` позволяет распознавать повтор, но порядок и единственная доставка не гарантируются. Нужны быстрая фиксация события, последующая обработка и сверка с актуальной записью через API, а также периодическая синхронизация на случай пропущенных событий. Не следует предполагать наличие стандартной HMAC-подписи, если она не подтверждена используемым механизмом. [Webhooks](https://developer.alteg.io/en/developers/openapi/webhooks), [изменение настроек](https://developer.alteg.io/en/developers/openapi/webhooks/update_event_notification_settings).

## 10. Что документация не позволяет считать окончательно подтверждённым

| Вопрос | Найденное ограничение | Как закрыть |
|---|---|---|
| Клиентский вход Altegio | `/user/auth` описан как вход по SMS, но схема тела содержит `login/password`, а секции авторизации не полностью согласованы | Выбрать собственную авторизацию + бизнес-API либо отдельно подтвердить публичный клиентский поток у Altegio и тестом |
| Перенос и получение по hash | Есть расхождения между `security` и описанием заголовка у отдельных публичных методов | Проверить выбранный тип токена и права на тестовой записи; не подставлять Business User вместо Booking User без проверки |
| Срок `record_hash` | В создании он описан как временный для удаления сразу после создания; гарантированного срока жизни для долгоживущей ссылки сайта нет | Согласовать собственный токен/сессию; проверить фактическую область действия upstream hash |
| `api_id` и повторное создание | В описании тип string, в schema number; гарантия устранения повторов не заявлена | Проверить фактический тип/поиск по внешнему ID; идемпотентность обеспечить собственным сервером |
| Имена/типы отдельных полей | Встречаются `category` vs prose categories, `seance_length` vs session_length, `seance_date` vs session_date; у SMS fullname/fulname; у некоторых datetime некорректный тип в schema | Снять обезличенные реальные ответы и зафиксировать контракт адаптера, не генерировать его вслепую из схемы |
| Состав данных филиала | Нет доступа к конкретному филиалу, токенов и образцов его ответов | Подтвердить реальные IDs, переводы, услуги, расписание, ресурсы, SMS, предоплату и права |

Эти расхождения не означают, что интеграция невозможна. Они определяют точные вопросы для следующего тестового этапа.

## 11. Контент, релиз и критерии готовности

От студии потребуются подтверждённые названия/цены/длительности, сотрудники и биографии, фото, описания услуг и подготовки, отзывы, материалы журнала, контакты и адрес, юридическое название, тексты privacy/terms, правила отмены/переноса, возрастная политика и противопоказания. В документации отмечено 36 `TODO(content)` на язык. Нужно заполнить их либо согласовать исключение соответствующей функциональности из релиза; просто скрыть плашки недостаточно.

По лендингам отдельно: утверждение скидки и условий, фактический срок ответа администратора, район/здание/карта, рабочий WhatsApp. Текущий оффер −20% — пример. Неподтверждённые фотографии нельзя выдавать за реальную студию или сотрудников. Существующие вопросы к формулировкам, лицензии и передаче отметок перечислены в проектной документации и требуют решения владельца проекта; этот аудит не является новым правовым заключением.

Техническая готовность включает:

- Production-сборку без подключённых mock-провайдеров, режимов ошибок и отладочных глобальных интерфейсов; тестовые fixtures остаются в тестах.
- Проверку реальных изображений, ошибок загрузки, длинных названий, пустого каталога и отсутствия окон; корректный RU/EN fallback.
- Доработку ограничений из KNOWN-ISSUES, в том числе баннера при недоступном localStorage и проверки внешних ссылок во встроенных браузерах на настоящем телефоне.
- Проверку фактических заголовков хостинга после подключения API: личные ответы без кеширования, защита ссылок от утечек, согласованная CSP. Нельзя считать все текущие заголовки отсутствующими: часть уже настроена по исторической документации.
- Мониторинг ошибок/доставки уведомлений/синхронизации без чувствительного содержимого. Поведение при недоступности API и Altegio должно быть явно определено.
- Реальный домен и метаданные, обновлённый sitemap/JSON-LD. Снятие `noindex`/запрета robots и заголовков хостинга — только с публичных страниц при готовности; кабинет и приватные ссылки не открываются для индексации.
- Сохранение принятых ограничений аналитики: не передавать контакты, зоны, заметки и токены; не возвращать автоматически аналитику в кабинет. GTM подключать после согласования состава данных. Уже исправленные в RC-10 URL-утечки не нужно вновь объявлять открытыми дефектами.

Тесты сейчас проверяют прототип. При подключении API понадобятся перехват запросов с fixtures вместо внутренних mock-hooks и отдельные интеграционные проверки тестового филиала. Текущий запрет внешних запросов в E2E необходимо осознанно адаптировать под собственный API, CAPTCHA и утверждённые источники медиа.

Приёмочные сценарии: создание и появление записи в Altegio; два пользователя на одно окно; повтор запроса без дубля; потеря ответа после создания; неверный/просроченный SMS; отказ доступа к чужой записи; отмена/перенос и запрет по правилам; изменение администратором; любой сотрудник; удалённая/отключённая услуга; клиент с несколькими карточками; визит без 3D-анкеты; доставка LP-заявки; корректность обеих локалей, календаря и аналитики. Исторически зелёный `gate` на заглушках этого не доказывает.

Онлайн-оплата не включена автоматически: если филиал требует предоплату, до релиза необходим отдельный совместимый поток или согласованная настройка услуг без обязательной предоплаты. Абонементы, сертификаты и программа лояльности — возможное расширение, в текущем интерфейсе обязательность не установлена.

## 12. Следующий этап после согласования

Пока достаточно определить: один или несколько филиалов; вариант Business User Token; собственная авторизация и связь с клиентом Altegio; политика SMS; доступный для теста набор данных; статическое обновление или другой способ рендеринга; источник редакционного контента; правила отмены/переноса и оплаты; процесс обработки LP-заявок.

После этого можно выполнить прямой локальный тест **вне браузера**: GET каталога, затем POST проверки окна (`book_check`, не создаёт запись). Создание через `book_record` — отдельная проверка на согласованных тестовых данных с последующей проверкой результата и очисткой тестовой записи. Сейчас ни один такой запрос не выполнялся.

Предварительная последовательность реализации: зафиксировать контракт и реальные образцы ответов → подключить каталог/сотрудников/расписание → основной и быстрый букинг → кабинет и ссылки → LP и уведомления → контент/обновление страниц → интеграционная приёмка и релиз. Это последовательность зависимостей; детальный план задач и оценки имеет смысл составлять после теста и принятых решений.

Токены для следующего этапа следует передавать через защищённое локальное/серверное окружение, не вставлять в исходники или этот документ.
