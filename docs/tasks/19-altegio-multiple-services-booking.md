# Задание этапа 19. Запись на несколько услуг к одному специалисту

**Статус — 19.1–19.3 реализованы.** Во всех действующих формах записи дать возможность выбрать несколько услуг и оформить запись в Altegio. Включить основной сценарий `/ru/booking/` и `/en/booking/`, форму на главной, формы рекламных страниц `/lp/a/` и `/lp/b/`, их существующие модальные и мобильные варианты в обеих локалях. Перед реализацией найти остальные действующие точки входа записи и включить их в проверку. Сейчас все услуги выполняет один специалист. Посетитель выбирает набор услуг, одного общего специалиста и одно время начала посещения.

**Требование к дизайну.** В каждой форме сохранить её существующий дизайн, последовательность и количество этапов, расположение полей и кнопок. Менять интерфейс только там, где это необходимо для множественного выбора и корректного отображения набора услуг. Сохранить собственный сценарий каждой формы, включая одноэкранный формат главной и существующие этапы лендингов. Новые шаги для выбора специалиста в формы, где такого шага сейчас нет, не добавлять. При необходимости минимального изменения объяснить в отчёте, какое требование оно обеспечивает.

Реализация разделена на 19.1–19.3. Выполнять части по отдельной команде пользователя. После каждой части записать результат, проверки и передачу следующей части в этот документ. Первая команда на реализацию запускает только 19.1.

## Согласованное поведение

1. Во всех формах множественный выбор появляется в существующем поле или шаге услуг. В основном букинге это шаг «Выберите услугу», следующий после выбора зон. Можно выбрать одну или несколько разных услуг и снять любую из них. Для перехода дальше или отправки нужна хотя бы одна доступная услуга. Рекомендация по зонам сохраняет прежнюю логику и не выбирает услугу автоматически. Каждая форма сохраняет свой текущий источник каталога, набор доступных услуг и действующие правила скидки. Выбор нескольких услуг должен учитывать эти правила для каждой услуги и общей суммы.
2. В существующем поле или шаге специалиста показывать один общий выбор для всего набора. При единственном подходящем сотруднике выбрать его автоматически и показать клиенту, сохранив сам шаг или поле. Если подходящих сотрудников несколько, показать их и существующий вариант «Любой специалист». Подходящий сотрудник должен выполнять каждую выбранную услугу. Список брать из Altegio, конкретный ID сотрудника в коде не закреплять. В формах с уже настроенным автоматическим назначением сотрудника сохранить этот способ и проверить, что назначенный сотрудник выполняет весь набор.
3. Если общего специалиста нет, показать понятное сообщение и дать изменить услуги в той же форме. Переход к времени и отправка недоступны. Расписание разных специалистов и отдельный выбор сотрудника для каждой услуги относятся к будущему расширению.
4. Дата и время выбираются для всего набора услуг. Окно должно вмещать полный сеанс. При отправке в стандартном случае создаётся одна запись с несколькими услугами, одним специалистом и временем начала.
5. Сводка, проверка перед отправкой и экран успеха показывают все выбранные услуги, общую цену или корректно обозначенную оценку, суммарную длительность, специалиста и время. На календарном событии и в подготовленном сообщении должны быть те же данные, если эти действия есть в текущем сценарии.
6. Поддержка нескольких услуг обязательна во всех действующих формах записи и вариантах их открытия. Отправка одной услуги также доступна. В существующих подготовленных WhatsApp-сообщениях, связанных с оформляемым набором, учитывать все выбранные услуги. Публичные страницы услуг, команды и цен сохраняют текущий дизайн и передают пресет услуги в обновлённый букинг.

## 19.1. Контракты и серверная поддержка набора услуг

### Что сделать

- Добавить представление `serviceIds` для набора услуг в общие контракты и серверные операции получения сотрудников, дат, времени и создания записи. Сохранить поддержку существующего `serviceId` для действующих клиентов API. Нормализовать вход один раз. Конфликтующие одиночное значение и массив отклонять понятной ошибкой. Пустой набор, некорректные ID и недоступную услугу проверять на сервере. Повторяющиеся ID не должны приводить к повторному начислению услуги.
- Подходящих специалистов определять по доступности всех выбранных услуг. При необходимости пересекать списки сотрудников по каждой услуге. Параметры запросов, ответы и ключи кеша должны учитывать весь нормализованный набор, локаль и специалиста. Вариант `staffId: 0` допускает только сотрудника, выполняющего весь набор.
- В `book_dates` и `book_times` передавать все выбранные ID через повторяемый `service_ids[]`. Использовать временную зону филиала и возвращённые Altegio значения `datetime`. Длительность полного окна, включая применимые перерывы, получать и интерпретировать по документации API. Не определять доступность набора по свободным окнам только одной услуги.
- Перед созданием проверить каждую услугу, доступность общего специалиста, актуальность окна, ограничения предоплаты и действующие требования филиала. Выполнить `book_check` с полным набором. Затем отправить один элемент `appointments` с `services: serviceIds`, выбранным общим `staff_id` и временем начала.
- Расширить подтверждение результата и ответы API так, чтобы они описывали весь выбранный набор. Сохранить обработку составных услуг и `parts`. Сверить через документацию и синтетические ответы поведение комбинаций с составной услугой. Не считать запись подтверждённой по наличию только первой выбранной услуги. Если полученный ответ не позволяет подтвердить весь результат, использовать предусмотренное состояние неопределённости.
- Включить весь набор услуг в сравнение запроса при идемпотентности и в проверку полученного результата на клиенте. Повтор одной отправки не создаёт дубль. Изменение набора после завершённой попытки создаёт новую логическую попытку. При неопределённом результате сохранять существующую защиту от повторного создания.
- Сохранить обработку конфликтов времени, ошибок CRM, SMS, лимитов запросов, контактов и комментария 3D-формы. Имя, телефон, email и согласие остаются обязательными. Существующие лимиты заметок и комментариев сохраняются.

### Приёмка части

Проверить синтетическим Altegio одну услугу, две и более услуги для каждого источника записи, полный набор параметров upstream, общего специалиста, отсутствие общего специалиста, отсутствие длинного окна, исчезновение одной услуги, конфликт слота и повтор отправки. Проверить обратную совместимость запросов с `serviceId` из главной формы и лендингов. Для лендингов проверить действующие скидки на весь набор услуг и соответствие серверных проверок текущим правилам оформления. Отдельно проверить прежнее создание составной услуги и подтверждение всего набора услуг. Реальные записи в филиале для этих проверок не создавать.

**Результат части** — сервер и контракты принимают набор услуг, существующие формы работают, целевые проверки проходят. Зафиксировать конкретные форматы запросов и ответов для подключения интерфейса в 19.2.

### Реализация 19.1

Основной поток в RU/EN, быстрая форма на главной и формы обоих лендингов используют один API записи. На каждом лендинге его вызывают формы в hero, финальном блоке и мобильной шторке. Страницы услуг и сотрудников, ближайшие окна, «Записаться снова» в личном кабинете и ссылки из меню, прайса и других разделов ведут в основной поток. Для ближайших окон профиля сохраняется отдельный `staff-today`.

| Метод и маршрут | Пример параметров | Поля успешного ответа в `data` |
| --- | --- | --- |
| `GET /api/booking/staff` | `?serviceIds=91201&serviceIds=13982355&locale=ru` | `{ serviceIds, staff: [{ id, name }] }` |
| `GET /api/booking/dates` | `?serviceIds=91201&serviceIds=13982355&staffId=0&locale=ru` | `{ serviceIds, staffId, dates: ["YYYY-MM-DD"] }` |
| `GET /api/booking/times` | `?serviceIds=91201&serviceIds=13982355&staffId=0&date=2026-12-01&locale=ru` | `{ serviceIds, staffId, date, times: [{ datetime, time, durationSeconds? }] }` |
| `POST /api/booking/record` | JSON из примера ниже | `201 { status: "created", recordId, serviceIds, datetime, staff?, durationSeconds?, parts? }` |

```json
{
  "serviceIds": [91201, 13982355],
  "staffId": 0,
  "datetime": "2026-12-01T13:15:00+04:00",
  "locale": "ru",
  "contact": {
    "fullname": "Тестовый Посетитель",
    "phone": "+971501234567",
    "email": "visitor@example.test"
  },
  "consent": true,
  "idempotencyKey": "63094e2f-7178-493b-aec2-28faa0789730"
}
```

- В GET передавать каждый ID отдельным параметром `serviceIds`, в JSON передавать массив целых положительных чисел. Сервер удаляет дубли и сортирует ID по возрастанию. Одиночный `serviceId` по-прежнему поддерживается в GET и POST с прежней формой ответа. Вместе с массивом он допустим, если совпадает с единственным ID нормализованного набора. Массив имеет приоритет для формы ответа. Ошибки выбора возвращают `400 INVALID_QUERY` или `400 INVALID_FIELDS` с полем `serviceIds`. Локаль GET по умолчанию `en`. [Контракты GET](../../src/lib/contracts/booking-services.ts) · [Контракт POST](../../src/lib/contracts/booking-record.ts)
- Для множественного запроса сервер получает свежий каталог и пересекает списки `book_staff` каждой услуги. Пустой список сотрудников, дат или времени — успешный ответ `200` с пустым массивом. Выбранный конкретный сотрудник вне пересечения даёт `404 STAFF_NOT_FOUND`. Клиент в 19.2 может выбрать единственный `staff[0].id` после успешного ответа и показать его в существующем поле или шаге. Лендинги продолжают передавать `staffId: 0`. Сервер для набора запрашивает даты и время у общих специалистов, а перед записью выбирает конкретного специалиста с подходящим окном и успешным `book_check`. Общий запрос доступности с исходным `staffId=0` для одной услуги сохраняет прежнее поведение.
- `book_dates` и `book_times` получают повторяемый `service_ids[]` для каждого ID. Дата и подпись времени рассчитаны в `Asia/Dubai`. В POST передавать исходный `datetime` из ответа без преобразования. Для окон `durationSeconds` берётся из `sum_length`, который Altegio описывает как общую длительность всех выбранных услуг, или из `seance_length` для одной услуги. При отсутствии общего значения или расхождении длительности между специалистами для одного начала поле опускается. Технические перерывы при доступности учитывает расписание Altegio. Длительность созданной записи берётся из `length`, а для подтверждённых частей — от первого начала до последнего окончания по их `length`. [Окна Online Booking](https://developer.alteg.io/en/public/openapi/online-booking/get_time_slots_for_booking) · [Длительность и технические перерывы](https://developer.alteg.io/en/b2b-v1/openapi/appointments/get_appointment_list)
- Перед созданием сервер проверяет каждую услугу и её предоплату, связь с общим специалистом и актуальность полного окна. `book_check` и `book_record` получают по одному элементу `appointments` с полным массивом `services`. Источники и дополнительные поля прежние. У 3D требуется `source: "3d"` и `body3d`. Для лендинга используются `source: "lp"`, допустимые `details`, `utm` и заметка. Имя, телефон, email и согласие обязательны. Офер A и B — 20% на первый визит по действующей конфигурации, включая диапазоны и цены «от». Цена и скидка остаются данными сайта для расчёта в интерфейсе. API записи передаёт в CRM услуги и контакты, а сумму CRM определяет по своим настройкам. В 19.2 применять общий офер к каждой услуге набора. [Правила цен](../../src/lib/catalog-service-price.ts) · [Конфигурация лендингов](../../src/lib/lp/config.json) · [Создание записи в Altegio](https://developer.alteg.io/en/public/openapi/online-booking/create_online_booking)
- Обычный набор подтверждается по деталям созданной записи. Все выбранные ID должны присутствовать по одному разу, время должно совпадать, а специалист — соответствовать общему назначению. Для одного комплекса сохраняются подтверждение целиком и разбиение на `parts: [{ recordId, title, datetime, durationSeconds?, staff? }]`, включая прежние комплексы с несколькими исполнителями компонентов. Для смешанного набора допускается ответ с несколькими частями, когда детали подтверждают каждый выбранный ID и одного общего специалиста. Online Booking не описывает однозначную связь развёрнутых компонентов со входным ID комплекса. Если детали содержат лишь компоненты и не позволяют подтвердить полный набор, API возвращает `202 { data: { status: "unknown" } }`. [Детали записи Altegio](https://developer.alteg.io/en/public/openapi/online-booking/get_online_booking_details)
- Отпечаток попытки содержит нормализованный набор. Повтор того же набора, включая иной порядок и дубли, использует прежнюю попытку. Тот же UUID с изменённым набором даёт `409 IDEMPOTENCY_CONFLICT`. Для нового набора после завершённой попытки нужен новый UUID. После `202 processing` или `202 unknown` сохранять защиту от создания дубля и не отправлять новый UUID автоматически. Клиентская проверка подтверждения сверяет весь нормализованный набор. Хранилище по-прежнему действует в одном процессе до 24 часов. [Задача общего хранилища](../POST-RELEASE-IMPROVEMENTS.md#pr-003-идемпотентность-записи-через-redis)
