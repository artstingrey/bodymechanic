# Задание этапа 20. Cloudflare Turnstile в формах записи

**Статус — реализовано в проекте.** Формы записи в RU/EN используют общий виджет `@marsidev/react-turnstile`. API проверяет токен перед созданием записи в Altegio. Сохранены порядок этапов и множественный выбор услуг из [задачи 19](19-altegio-multiple-services-booking.md). Рабочий виджет на `thebodymechanic.io` в рамках локальной проверки не проверялся.

## Настройки, предоставленные пользователем

| Параметр | Значение |

Обе переменные уже настроены пользователем. Файлы `.env`, конфигурационные файлы с фактическими ключами и архив `bodymechanic-site-main.zip` не читать. Значения ключей не запрашивать, не печатать и не записывать в задание или исходники. Использовать переменные по указанным именам. Секрет доступен только серверному коду. `TURNSTILE_SITE_KEY` передаётся в клиентский код при сборке через конфигурацию Next.js.

## 1. Общий компонент и размещение виджета

- Установить `@marsidev/react-turnstile` и обновить файл зависимостей и lock-файл. Создать общий клиентский компонент для всех форм, переиспользующий библиотеку и её жизненный цикл. Скрипт Cloudflare загружается один раз на документ, каждый экземпляр формы получает отдельный виджет и состояние токена.
- На главной разместить виджет в существующем `.captcha.cap` внутри [QuickForm](../../src/components/booking/QuickForm.tsx). Снять `hidden` с рабочего контейнера. Сохранить классы и положение блока перед действиями формы. При необходимости заменить тег `p` на подходящий контейнер для содержимого виджета.
- В 3D-букинге разместить виджет в существующем `.captcha` внутри [StepReview](../../src/components/booking/steps/StepReview.tsx). Снять `hidden`. Использовать положение блока на существующем шаге проверки. Заменить демонстрационное содержимое настоящим виджетом.
- В [LandingBookingFlow](../../src/components/lp/LandingBookingFlow.tsx) подключить тот же компонент к финальному этапу отправки. Охватить `/lp/a/` и `/lp/b/`, формы в верхней и нижней секциях и их существующие мобильные и модальные варианты. Если готового контейнера нет, добавить минимальный блок `.captcha` рядом с подтверждением и кнопкой отправки внутри текущего этапа. Это необходимо для общей защиты `POST /api/booking/record` во всех сценариях.
- Сохранить дизайн остальных полей, кнопок и этапов. Виджет должен действительно отображаться в назначенных контейнерах. Использовать режим Managed и обычную видимость `appearance: 'always'`. Дополнительный этап проверки не создавать. Инициализировать виджет при открытии соответствующего блока формы. Формы, скрытые в закрытой панели, не должны получать действующие невидимые интерактивные проверки.
- Проверить размеры на узких экранах. Учитывать минимальную ширину стандартного и flexible-вариантов, при необходимости использовать компактный размер. Виджет не обрезать, не масштабировать CSS-трансформацией и не перекрывать соседними элементами.
- Задать локаль виджета RU/EN и согласованное значение `action: 'booking'` для всех форм. При загрузке, ошибке, истечении и повторе показывать понятное состояние в текущем блоке, использовать словари проекта и доступные уведомления.

## 2. Жизненный цикл токена и отправка

- Получать токен через `onSuccess`, очищать при `onExpire`, ошибке, сбросе и размонтировании. Учитывать `onTimeout` и недоступность скрипта. Токен действителен 300 секунд и предназначен для однократной проверки. Для повторной новой попытки после окончательного отказа сервера получать свежий токен через штатный reset/refresh.
- Хранить токен только в памяти текущей формы. Передавать его в `POST /api/booking/record`, например в поле `captchaToken`. Не сохранять в черновиках, результатах, `localStorage`, `sessionStorage`, URL, аналитике и логах. В Altegio токен не передавать.
- Согласовать блокировку отправки с существующей валидацией и состояниями формы. При неготовой капче отправка недоступна, рядом видно, почему. Потеря или истечение токена не очищает услуги, сотрудника, время, контакты, заметки и согласие.
- После отправки сохранить существующий сценарий результата. При `processing` или `unknown` посетитель проверяет состояние предыдущей попытки. Повторная капча сама по себе не запускает новое бронирование.
- Адаптировать общий [useBookingAttempt](../../src/components/booking/useBookingAttempt.ts), [отправку](../../src/components/booking/booking-submit.ts) и обработку ошибок каждой формы. Не переводить окончательный отказ капчи в `unknown`, если запись в Altegio ещё не отправлялась.

## 3. Проверка на сервере и идемпотентность

- Расширить [контракт](../../src/lib/contracts/booking-record.ts), [разбор запроса](../../src/server/booking/record-request.ts) и [маршрут создания](../../src/app/api/booking/record/route.ts). Для каждой новой попытки создания обязательны корректный токен и успешная серверная проверка. Прямой HTTP-запрос к API без токена не создаёт запись.
- Сделать общий серверный вызов `POST https://challenges.cloudflare.com/turnstile/v0/siteverify` через `fetch`. Использовать `TURNSTILE_SECRET_KEY`, токен и, если передаётся `remoteip`, только уже установленный сервером доверенный IP. Проверять формат и длину токена по документации, HTTP-ответ, структуру JSON и `success === true`. Проверять `hostname` для `thebodymechanic.io` и `action === 'booking'`. Ожидаемые значения определяет сервер.
- Ограничить время ожидания Siteverify. При таймауте, неверном ответе, недоступном сервисе, отклонённом токене или отсутствующей конфигурации новую запись не создавать. Вернуть различимые ошибки проверки и недоступности, обработать их в каждой форме с возможностью повторить проверку. Отсутствие настроек не должно ломать сборку и просмотр сайта.
- Проверять капчу до вызовов, создающих запись в Altegio. Сохранить действующие проверки origin, тела запроса, согласия, ограничений и лимитов. Публичные чтения каталога, дат и времени продолжают работать в прежнем сценарии.
- Учесть текущую [идемпотентность](../../src/server/booking/record-store.ts). Сейчас fingerprint строится по всему нормализованному запросу. Токен капчи должен быть отделён от сохраняемых данных бронирования и fingerprint. Обновление токена не превращает ту же запись в другую логическую попытку и не вызывает `IDEMPOTENCY_CONFLICT` само по себе.
- Повтор уже принятой попытки с тем же ключом и теми же данными возвращает предусмотренный результат, не расходуя повторно одноразовый токен. Изменение данных записи с тем же ключом по-прежнему вызывает конфликт. При конкурентных запросах сохраняется единственное создание записи. Окончательный отказ капчи до отправки в CRM не должен навсегда блокировать исправленную попытку в состоянии `processing` или `unknown`.
- Разделить повтор сетевого запроса Siteverify и новое решение капчи. При повторе той же проверки использовать его `idempotency_key` согласно документации. Смена токена требует корректного жизненного цикла новой проверки. Не полагаться на мгновенную глобальную блокировку повторного токена как на замену идемпотентности записи.
- [Маршрут статуса](../../src/app/api/booking/record/status/route.ts) сохраняет существующую проверку `idempotencyKey` и `recoveryKey` и не создаёт запись. Для восстановления статуса уже принятой попытки капча повторно не требуется.

## 4. Локальная проверка и документация

- Рабочий виджет зарегистрирован на `thebodymechanic.io`. Для localhost, автоматизированного браузера и синтетического Altegio использовать официальные тестовые ключи или тестовые ответы Siteverify в изолированном окружении проверки. Значения тестовых переменных задавать процессу проверки, сохранив пользовательские конфигурационные файлы.
- Учесть, что официальный успешный ответ с dummy-ключом возвращает `hostname: 'example.com'` и не содержит `action`. Положительную и отрицательную проверку реальных `hostname` и `action` тестировать контролируемыми ответами Siteverify. Тестовый адаптер должен быть изолирован от рабочего приложения. Рабочую проверку домена и action ради теста не ослаблять.
- Проверить действующую CSP. При наличии ограничений разрешить необходимые официальные источники Cloudflare по документации. Скрипт загружать с официального адреса. Pre-clearance остаётся Disabled. Обновить описание настроек и проверок в соответствующих документах без фактических значений ключей.

## Приёмка

- На главной виджет виден в `.captcha.cap`, на шаге проверки 3D-букинга в `.captcha`. На обоих лендингах он встроен в текущий этап отправки. Проверены RU/EN, телефон и компьютер, открытие и повторное открытие панелей, несколько форм на одной странице и отсутствие повторной загрузки скрипта.
- Во всех формах запись с одной и несколькими услугами проходит только после успешной серверной проверки. Без токена, с поддельным, истёкшим или отклонённым токеном, с неверным `hostname` или `action` вызова создания записи в Altegio нет. Сбои Cloudflare сохраняют заполненные данные и позволяют повторить проверку.
- Проверены пять минут ожидания, reset и повтор после окончательного отказа, переход назад и вперёд, двойной клик, конкурентные запросы, сетевой обрыв после отправки и восстановление результата. Смена токена не ломает fingerprint, уже принятую попытку и проверку её статуса.
- Ни секрет, ни токены не попадают в клиентский bundle, хранилища, URL, логи и аналитику. Проверять это без чтения фактических ключей. Публичный Site Key допускается в клиентском bundle по назначению.
- С синтетическими Cloudflare и Altegio запустить целевые проверки капчи, создания записи, множественного выбора, главной формы и лендингов, а также `npm run lint`, `npm run typecheck`, `npm run i18n` и `npm run build`. Реальные записи для автоматизированной проверки не создавать.
- В финальном отчёте указать изменённые формы, фактически пройденные проверки и отдельно отметить, проверен ли рабочий виджет на `thebodymechanic.io`. Локальный тест с dummy-ключом подтверждает только тестовый сценарий.
