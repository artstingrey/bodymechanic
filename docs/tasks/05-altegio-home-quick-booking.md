# Задание этапа 5. Запись через форму на главной

**Статус:** подготовлено к реализации. Выполнять только ту часть, которую пользователь явно назвал в чате. После её реализации проверить результат, сообщить итоги и остановиться до команды на следующую часть. Стартовая команда для реализации — «Выполни 5.1».

Цель этапа — посетитель выбирает одну услугу, специалиста или вариант «Любой специалист», дату и время, отправляет форму и получает подтверждение созданной в Altegio записи. Целевая форма — `section.section.section--sand.home-sec[aria-labelledby="form-title"] form.qform` на `/ru/` и `/en/`. В [общей карте](../ALTEGIO-IMPLEMENTATION-PLAN.md#5-карта-внедрения-по-разделам) номер 5 ранее относился к страницам команды. Для этого задания этап 5 — быстрая запись на главной. Страницы команды, `/booking` с 3D, запись со страниц услуг, кабинет, перенос и отмена, лендинги и платежи идут отдельными задачами.

## Исходные условия

- Прочитать `AGENTS.md`, [план интеграции](../ALTEGIO-IMPLEMENTATION-PLAN.md), [контракт записи и заглушек](../BACKEND-CONTRACT.md#3-запись-на-приём-функции-и-маршруты) и [инструкцию smoke-проверки](../../tools/altegio-smoke/README.md). Перед правками Next.js прочитать руководства установленной версии в `node_modules/next/dist/docs/` и сверить Context7. Файлы `.env` не открывать. Для запросов к филиалу использовать уже настроенное окружение.
- Точки входа — [главная](../../src/app/%5Blocale%5D/page.tsx), [`QuickForm`](../../src/components/booking/QuickForm.tsx), [каталог](../../src/server/catalog/services.ts), [сотрудники по услуге](../../src/server/catalog/staff.ts) и [серверный транспорт Altegio](../../src/server/altegio/client.ts). Сейчас форма получает демоуслуги от главной, отправляет `staffId: 0` для всех случаев и получает демодаты, время и результат из `src/lib/api`. Сохранить внешний вид, поля и RU/EN. В части 5.2 скрыть блок «Проверка, что вы не робот» через `hidden`, сохранив элемент и тексты. Реальный API не ожидает CAPTCHA и не получает `demo-quick-form`.
- Email обязателен для быстрой записи по решению пользователя. Пометить поле обязательным в RU/EN. Форма и сервер отклоняют пустой email и неверный формат. Проверить также часовой пояс, требование SMS и обязательную предоплату. [Спецификация Altegio Online Booking](https://developer.alteg.io/en/public/openapi)
- SMS-подтверждение вынесено в отдельный этап по решению пользователя. Сквозную проверку части 5.4 провести на филиале без обязательного SMS. Если Altegio требует код, сообщить, что выбранный филиал его требует. Если у конкретной услуги обязательна предоплата, доступность остальных услуг сохраняется, а запись без поддерживаемого способа оплаты для этой услуги не отправляется. Отразить ограничение в RU/EN и не показывать подтверждение записи на непроверенный результат.
- Возраст и самочувствие оставить в форме. Для стандартного поля клиентской карточки Business Management API принимает точную дату рождения `birth_date`. Текущая форма собирает возраст в годах. Для передачи числа лет подходит настроенное дополнительное поле карточки `custom_fields`; ключ и тип зависят от филиала. Дату рождения из возраста не вычислять. Способ хранения возраста согласовать перед передачей. [Поля карточки клиента](https://alteg.io/en/support/knowledge-base/4861029589661) · [Business Management API v1](https://developer.alteg.io/_bundle/en/b2b-v1/openapi.json)
- Целевое место для дополнительных ответов — **Notes about client** в клиентской карточке. Публичный `book_record.comment` относится к конкретному визиту. У Business Management API v1 есть поле карточки `comment` в `PUT /client/{location_id}/{id}` и отдельный `POST /locations/{location_id}/clients/{client_id}/comments` для добавления записи в историю комментариев без перезаписи предыдущих, с лимитом 255 символов. Для истории нужны права `clients_access` и `client_comments_add_access`, а запрос выполняется с Partner Token и Business User Token. Перед включением передачи подтвердить на тестовой карточке, какой из этих механизмов отображается в нужном блоке админки, как получить ID карточки, связанной с созданной записью, и как сохранить существующий текст. До этой сверки значения дополнительных полей не передавать. Ошибка сохранения заметки не повод повторять создание визита. Имя, телефон, email, ответы о самочувствии и служебные данные Altegio не отправлять в аналитику и логи. Согласие на обработку данных проверять на сервере и фиксировать по правилам проекта. [Business Management API v1](https://developer.alteg.io/_bundle/en/b2b-v1/openapi.json)

## 5.1. API каталога и доступности

1. Использовать текущий каталог услуг как серверный источник реальных ID и названий. Для специалистов использовать связь с одной услугой через `book_staff` с `service_ids[]`, как на детальной странице. Вернуть минимальные публичные поля. Список назначенных сотрудников и наличие доступных окон — разные данные. Для дат и времени обращаться к Altegio свежими запросами и возвращать `Cache-Control: no-store`, без четырёхчасового кеша каталога.
2. Реализовать read-only API сайта. Предлагаемые маршруты — `GET /api/booking/staff?serviceId=&locale=`, `GET /api/booking/dates?serviceId=&staffId=&locale=` и `GET /api/booking/times?serviceId=&staffId=&date=&locale=`. Для дат использовать `book_dates` и `data.booking_dates`. Для времени использовать `book_times/{location_id}/{team_member_id}/{date}` с `service_ids[]`. Передавать `staffId: 0` для любого специалиста, а при выборе конкретного сотрудника передавать его реальный ID. Сохранять `datetime` из Altegio со смещением и триаду услуга — специалист — время. Отображать время в `Asia/Dubai`, одинаково для посетителей в разных поясах. Проверить даты на границе месяца, используя подтверждённый горизонт бронирования филиала.
3. Проверять допустимые query-параметры, локаль, ID, наличие публичной услуги, связь выбранного специалиста с ней и календарную дату. Различать пустой список, неверный запрос, недоступность и ограничение частоты. Сохранять `Retry-After` там, где он приходит. Путь Altegio и идентификатор филиала формирует сервер. Контракт должен выдавать только поля, нужные форме.

**Приёмка:** синтетический upstream проверяет параметры, разные услуги и сотрудников, `0`, пустой день, 429, таймаут и сохранение `datetime` с часовым поясом. При доступном филиале выполнить GET-сверку для конкретного сотрудника и режима «Любой специалист». В этой части форма ещё не подключается к новому API, POST-запросы в CRM не выполняются.

## 5.2. Подключение каскада полей формы

1. Передать форме услуги из общего каталога Altegio. Переиспользовать правила текста RU/EN по реальному ID из секции услуг. Загрузка каталога и сбои внутри формы не должны задерживать основной контент главной. Не подставлять демонстрационные ID, цены или окна при отсутствии данных.
2. При выборе услуги заново загрузить список специалистов, сбросить предыдущего специалиста, дату и время. Даты загружаются для новой услуги и выбранного специалиста, включая режим «Любой специалист». Смена специалиста сбрасывает дату и время. Смена даты сбрасывает время и загружает окна на этот день. Отменять запросы или игнорировать ответы от предыдущего выбора. Время в контроле должно принадлежать текущему сочетанию услуги, специалиста и даты.
3. Показать отдельные состояния загрузки, пустого результата, ошибки и повтора. Оставить видимыми существующие поля и кнопки. Скрыть только индикатор CAPTCHA. Кнопку отправки сохранить с объяснимым состоянием недоступности до подключения API создания. Форма с реальными ID не вызывает демо-`postRecord` и не показывает демоподтверждение.

**Приёмка:** проверить RU/EN, мобильную и широкую вёрстку, последовательный выбор и быстрые переключения с ответами не по порядку, вариант «Любой специалист», отсутствие дат или окон, ошибку и повтор. Проверить, что email отмечен как обязательный и что ввод контактных данных не теряется при смене услуги. Адаптировать существующие тесты главной, которые ожидают демо-ID в `qf-service`.

## 5.3. Серверный API создания записи

1. Реализовать `POST /api/booking/record` для одной услуги и одного окна. Принять выбранные `serviceId`, `staffId` (`0` допустим), исходный ISO `datetime`, локаль, контакты, согласие и ключ идемпотентности. Валидировать структуру, длины, телефон, email, согласие и актуальный выбор на сервере. Переиспользовать существующий транспорт с серверным токеном, таймаутом и безопасным логированием. `book_check` может вернуть пустой `201` или документированный JSON с успешным результатом. Проверка выполняется на сервере непосредственно перед `book_record`. В промежутке окно может занять другой посетитель. Обработать конфликт от обеих операций.
2. Возвращать `created` только после валидного ответа Altegio, содержащего созданную запись. Возвращать форме минимальный результат. По необходимости читать подтверждённые сведения о визите сервером, используя `record_hash` только на сервере. Для режима «Любой специалист» показывать назначенного сотрудника, если Altegio его подтвердил. Не показывать `0` или выбранный вариант как имя назначенного человека. Различать ошибки полей, занятое окно, отсутствие специалиста, обязательный SMS, лимиты и неизвестный результат. При таймауте после отправки не утверждать, что запись не создалась. Очередь и Telegram в эту часть не входят.
3. Защитить запись от двойного нажатия, параллельного повтора и повторной отправки после потери ответа. Хранить ключ, отпечаток запроса и состояние атомарно. Один ключ относится к одной попытке бронирования. Повтор с тем же телом получает сохранённый результат или состояние обработки. Тот же ключ с изменёнными данными отклоняется. Срок ключа по ТЗ — 24 часа. Для публичного запуска использовать общее устойчивое хранилище, чтобы перезапуск и второй экземпляр не создавали дубли. Если такого хранилища ещё нет, описать зависимость в отчёте о 5.3. Не использовать `api_id` как гарантию дедупликации и не повторять POST автоматически при неизвестном исходе. Добавить существующие требования проекта по ограничениям частоты и проверке источника POST. [Серверные требования проекта](../SECURITY.md#что-обязана-сделать-техническая-команда-на-стороне-сервера)

**Приёмка:** на синтетическом upstream проверить пустой `201` у проверки, подтверждённое создание, конкурирующее бронирование одного окна, повтор одного ключа, изменённое тело, потерю ответа после записи, невалидное подтверждение, отсутствие согласия, SMS-ошибку и 429. Пустой email и неверный формат отклоняются до обращения к Altegio. В этой части UI отправки не подключается. Реальных записей для тестов части 5.3 не создавать.

## 5.4. Отправка формы и сквозная приёмка

1. Связать отправку формы с готовым API. После подтверждённого `created` показать успех и подтверждённые сведения о визите. При конфликте обновить даты или время, снять устаревший выбор и сохранить контакты. При неизвестном исходе сообщить, что создание не подтверждено. Состояние формы сбрасывается при обновлении страницы, автоматического повтора отправки нет. `booking_success` отправлять только после подтверждённого создания и с учётом действующих правил аналитики и согласия.
2. Прогнать форму целиком с синтетическим upstream в обеих локалях. После согласования тестовой услуги, сотрудника, окна и контактов проверить одну настоящую запись через форму на филиале без обязательного SMS и подтвердить её появление в Altegio. Учесть, что у настоящей записи могут быть уведомления. Публичное включение формы для посетителей — отдельное решение о выкладке. После пользовательской команды реализовать только 5.4 и отчитаться о фактическом окружении проверки.

## Отчёт после каждой части

Указать реализованные маршруты и состояния формы, пройденные проверки и оставшиеся зависимости. Отдельно отмечать результаты fixture, GET-сверки и создания настоящей записи. Выполнить `lint`, `typecheck`, `i18n` и целевые тесты части на production-сборке. Проверить, что сборка не требует доступной CRM, а страницы и сценарии вне быстрой формы сохраняют текущее поведение. В общем плане записать итог завершённой части. Следующую часть запускать только после команды пользователя.
