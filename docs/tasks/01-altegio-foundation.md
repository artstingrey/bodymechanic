# Задание для чата 1: серверная основа интеграции Altegio

Статус: к реализации. Зависимость: успешный локальный тест уже выполнен пользователем, код находится в `tools/altegio-smoke`. Следующий потребитель — секция услуг на главной, описанная в [задании 2](C:/next-js-projects/body-mechanic/docs/tasks/02-altegio-home-services.md).

## Цель и границы

Перевести проект в серверный режим Next.js, организовать общую server-only интеграцию и реализовать получение нормализованного каталога через серверную функцию и `GET /api/catalog/services`.

В этом задании не подключать карточки, команду, букинг, кабинет или LP. Не создавать реальные записи, не менять настройки Altegio. Не создавать отдельный API-сервер, не переносить в production локальный smoke-сервер. Сохранить действующие интерфейсы и демонстрационные сценарии до их отдельных этапов.

Рабочая папка: `C:\next-js-projects\body-mechanic`. Архив `bodymechanic-site-main.zip` не читать. Для разработки ветки использовать принятые правила проекта; не публиковать и не менять удалённый хостинг как побочный эффект локальной реализации.

## 1. Режим запуска приложения

1. Убрать `output: 'export'`; обычный Node runtime, `next build` + `next start`. `output: 'standalone'` сейчас не требуется, если нет отдельной задачи контейнеризации.
2. Добавить корректный `start`; привести `build` и `serve` к серверному режиму. Не оставлять основную команду просмотра на старом `out/`.
3. Исключить `fix-export-segments.mjs` и `lp-postexport.mjs` из нового build-пайплайна. Первый исправляет только static export; второй также исправлял реальную проблему шрифтов. Проверить предзагрузки сайта и LP после перехода. Не пытаться вслепую патчить `.next` прежним скриптом; при регрессии исправлять настройку шрифтов/исходники и сохранять разделение раскладок.
4. Сохранить `trailingSlash`, локали, текущую логику выбора языка на `/`, 404, private metadata и noindex. API должен работать вне языкового префикса и не перенаправляться на HTML локали.
5. Не удалять все `generateStaticParams`/`dynamicParams` механически. Проверить конкретные динамические маршруты. В частности, прежняя работа произвольной ссылки `/account/record/{id}/{hash}/` обеспечивалась rewrite статического хостинга: нужен эквивалентный маршрут в Node-режиме без получения реальных персональных данных на этом этапе.
6. Перенести необходимые заголовки из старого сервера/описания хостинга в новый применимый механизм. Не объявлять настройку удалённого хостинга выполненной. Для приватных страниц сохранить no-referrer и no-store; для API исключить кеширование ошибок в браузере/CDN.
7. Обновить README и CONFIG-DEPLOY: цель — Node Web Service, а не публикация каталога `out`. Секреты нужны в runtime, не в браузере. Указать реальные команды локального запуска и будущей выкладки.

## 2. Серверная конфигурация и транспорт

Создать структуру из общего плана. Серверные модули защищать `import 'server-only'`. Общие DTO не должны импортировать эти модули. Никаких реэкспортов server-only через существующий универсальный `src/lib/api/index.ts`.

Конфигурация:

- `ALTEGIO_LOCATION_ID` — положительное целое, филиал задаёт сервер;
- `ALTEGIO_PARTNER_TOKEN` — только значение токена, без Bearer;
- при необходимости `ALTEGIO_CURRENCY` — проверенная валюта филиала, без неявного копирования из демо-кода;
- базовый production URL — `https://api.alteg.io/api/v1`; не разрешать браузеру менять его, филиал, токен или path upstream;
- пример настройки без значений секретов. Локальный файл должен игнорироваться Git. Не переносить имя, телефон, email и datetime smoke-записи в настройки приложения.

Читать и валидировать секреты при обращении к серверному сервису, не падать при импорте модуля во время сборки. Сборка без токена не должна обращаться к CRM. При реальном запросе без конфигурации возвращать безопасную управляемую ошибку, не демо-каталог.

Транспорт:

- общий `fetch` с нужными Accept/Authorization, таймаутом и `redirect: 'error'`;
- корректная обработка не-JSON, пустого тела, HTTP-ошибки и `success: false` даже при HTTP 200;
- сообщение наружу без сырого ответа, токена, URL с hash и деталей клиентской карточки;
- ограниченная диагностика: операция, статус, длительность, собственный requestId при наличии; не логировать headers и тело;
- автоматические повторы не нужны для первого GET. Не вводить общий retry для будущих POST создания записи;
- не публиковать endpoint вида `/api/altegio?path=...`, команды `book`/`verify` из smoke или технический просмотр конфигурации.

Business User Token для текущего публичного каталога не требуется, если фактический ответ не покажет иное. Не внедрять бизнес-авторизацию и пользовательские сессии заранее.

## 3. Каталог и публичный контракт

Источник: `GET /book_services/{location_id}?without_seances=1`. Выполнить разрешённый read-only запрос с существующей локальной конфигурацией, не выводя секреты. Сохранить только обезличенный минимальный fixture формы ответа, нужный для тестов преобразования.

Реализовать `getCatalogServices(locale)` и Route Handler согласно DTO общего плана. Если фактический ответ требует поправки DTO, сделать её здесь, описать в документе и не оставлять второму чату угадывать поля.

Правила преобразования:

1. Проверить envelope и массив услуг, положительные ID, непустое название. Сбой схемы верхнего уровня — ошибка, а не успешный пустой каталог.
2. Не выдавать поля, которых нет в контракте. Категории нормализовать по фактическому полю ответа (`category` и описание `categories` в документации расходились).
3. Учитывать признаки публикации/доступности только после проверки их реального смысла. Не превращать отсутствие свободных окон в удаление услуги из каталога.
4. Не переносить `101`, `sports`, `hasCms`, демонстрационные цены или тексты. Не связывать услугу с демо по названию или индексу массива.
5. Корректно различать `0` и отсутствие цены. Не вычитать скидку повторно и не объявлять цену «по запросу» на основании произвольного нуля.
6. Длительность переводить из секунд только для подтверждённого поля ответа. Если длительность зависит от сотрудника и сейчас неизвестна — `null`.
7. Описание брать только из поля публичного описания, не из внутреннего комментария. HTML приводить к безопасному тексту подходящим способом; если публичный источник не подтверждён — `null`.
8. URL изображения валидировать, разрешать ожидаемый безопасный протокол. На этом этапе сервер не скачивает произвольные изображения и не создаёт универсальный image-proxy.
9. Реально доступные локализованные поля использовать по документации. Если их нет, сохранять исходный текст; редакционные переводы добавит следующий этап.

HTTP API:

- `GET /api/catalog/services?locale=ru|en`, locale по умолчанию `en`;
- 200 только при корректно полученных данных; настоящий пустой массив — допустимый 200;
- неверные параметры — 400;
- недоступная конфигурация/доступ к upstream — безопасный 503;
- таймаут upstream — 504;
- некорректный ответ upstream — 502;
- upstream 429 — временная недоступность с документированным кодом и допустимым `Retry-After`, без бесконечных повторов;
- публичный код ошибки не должен заставлять посетителя вводить токен Altegio или авторизовываться в CRM.

Route Handler только проверяет вход, вызывает общий сервис и формирует HTTP-ответ. Нормализация и правила данных не дублируются в нём и будущей секции главной.

## 4. Кеш и сборка

Начальное правило: кешировать успешный проверенный публичный каталог на 60 секунд, учитывать филиал и параметры, влияющие на данные. Не кешировать персональные данные, будущие записи и ошибку как успешный пустой список.

Для текущего `cacheComponents: false` использовать штатный механизм Next.js: например, кеш функции нормализации через `unstable_cache`, который сохраняет результат после проверки. Конкретный механизм подтвердить по локальным документам. Не считать module-level Map полноценным серверным кешем и не писать данные CRM в репозиторий.

Указать семантику устаревания: time-based revalidation может вернуть предыдущие данные во время обновления и при ошибке обновления; 60 секунд не обещают жёсткого максимального возраста. На этом этапе не строить отдельную очередь обновлений. Ошибка без ранее доступного каталога должна быть видна потребителю.

HTTP-ответ Route Handler можно отдавать с `Cache-Control: no-store`: кеш данных остаётся серверным и общим для API и Server Component. Не создавать независимые несогласованные кеши на каждый слой.

У server-side потребителя следующего этапа запрос должен происходить во время обращения пользователя. В частности, `connection()` перед загрузкой данных позволяет исключить её из prerender; не предполагать, что удаление `output: export` само по себе отменило build-time fetch. Механизм выполнения и кеширование данных — разные решения.

## 5. Проверки и миграция тестового окружения

Нельзя закончить этап с зелёным тестом, который на самом деле обслуживал старый `out/`.

В зоне изменения:

- `playwright.config.ts` — webServer на production Node-приложение;
- `e2e/global-setup.ts` — проверка целевого процесса/сборки вместо обязательного `X-Served-Out`;
- `e2e/helpers.ts` — инвентарь страниц без обхода `out/`, сохранить покрытие маршрутов и локалей;
- `e2e/seo.spec.ts` и другие тесты, читающие экспортированные HTML/RSC-файлы: проверять эквивалентные свойства через HTTP/DOM либо соответствующий актуальный артефакт, не удалять требования безопасности и SEO;
- `scripts/clean-build.mjs` — проверять серверную сборку и реальные маршруты; адаптировать проверку неизменности CSS, не требовать `out/index.html`;
- `scripts/serve-out.mjs` и старые postexport-скрипты не должны оставаться основным способом запуска.

Проверки интеграции должны быть детерминированными: fixture/мок транспорта или локальный имитатор upstream в тестовом окружении. Тестовый транспорт не доступен через query-параметры и не может незаметно включаться в обычном production-запуске. Клиентский `page.route()` не перехватывает запросы, сделанные сервером Next.js; учесть это при устройстве E2E для следующего этапа.

Минимум проверки нового слоя:

- нормальный ответ, пустой каталог, отсутствующие необязательные поля, цена 0;
- неверная schema, не-JSON, `success: false`, 401/403/429/5xx и таймаут;
- параметр locale и невозможность подменить upstream/филиал через HTTP;
- отсутствие токена/raw ответа в публичном JSON и клиентском JS;
- build без токена/доступа к Altegio, контролируемый ответ при runtime без конфигурации;
- реальный read-only GET из запущенного приложения при наличии локальных доступов;
- smoke старых RU/EN, LP, кабинета, 404 и прямых ссылок после перехода на Node.

Выполнить lint, typecheck, i18n, build и соответствующие адаптированные проверки. Фиксировать реальные результаты; не объявлять старый полный gate выполненным, если запускался только новый smoke. Новые E2E не должны обращаться к настоящей CRM на каждом CI-прогоне.

## Критерии завершения и передача

Этап завершён, когда серверный Next.js запускается, каталог получается через общий сервис и HTTP, контракт зафиксирован, сборка не требует доступной CRM, секреты не выходят на клиент, а базовые маршруты и проверки работают в новом режиме. Дизайн и источники данных существующих страниц пока не переключены.

Обновить раздел передачи в общем плане:

- фактические пути и сигнатуру `getCatalogServices`;
- DTO и пример ответа без приватных данных;
- env-переменные и безопасный способ их локального задания;
- команды build/start/test, механизм кеша и ошибки;
- результаты реального GET и автоматических проверок;
- ещё не перенесённые проверки, если они объективно остались, с явным статусом незавершённости;
- требуемые действия на хостинге, которые локально не выполнялись.

Переходить к реализации карточек в этом чате не нужно: это отдельное задание.
