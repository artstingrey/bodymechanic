## 3. Источник данных и правила публикации

Использовать `GET https://api.alteg.io/api/v1/book_staff/{location_id}` через существующий серверный клиент. Филиал и Partner Token — только из серверной конфигурации. Не создавать второй HTTP-клиент, отдельный backend или универсальный прокси.

На 14.11.2026 проверена [официальная спецификация Online Booking](https://developer.alteg.io/en/public/openapi), операция `GET /book_staff/{location_id}`:

- Требуется Bearer Partner Token, `Accept: application/vnd.api.v2+json`.
- `data` — массив сотрудников. Для главной запрос без `service_ids[]` и `datetime`: состав команды не должен зависеть от выбранной услуги или конкретного времени.
- Параметр `without_seances` здесь не документирован; не копировать его из `book_services`.
- Доступны `id`, `name`, `specialization`, `position`, `avatar`, `avatar_big`. `position` может быть объектом или пустым массивом, пример также содержит пустой объект.
- `bookable` означает наличие свободных сеансов. **Не исключать сотрудника только из-за `bookable: false`** и не использовать этот флаг как признак увольнения или скрытия.
- В схеме есть `hidden` и `fired` как числовые признаки. Явно скрытых/уволенных не публиковать. До реализации сверить значения флагов с актуальной документацией/обезличенным ответом; зафиксировать нормализацию и тесты. Отсутствие необязательного флага не равно `true`. Не придумывать значения перечисления `status`.
- Сохранять порядок ответа: документация описывает порядок по весу. Не сортировать по имени и не ограничивать первыми N сотрудниками без отдельного требования.
- `information` содержит HTML; для этой секции биографии не нужны. Не выводить его через `dangerouslySetInnerHTML` и не передавать в публичный DTO.

Публичный Online Booking — источник опубликованной команды, а не всех пользователей бизнес-аккаунта. Если фактический состав отличается от ожидаемого, записать причину/неопределённость, а не незаметно переходить на бизнес-метод с расширенными правами. Число карточек не зашивать.

## 4. Структура и контракт

| Место | Изменение |
|---|---|
| `src/server/altegio/staff.ts` | `fetchBookStaff(locationId, locale)` через общий `altegioGet` |
| `src/server/catalog/staff.ts` | `getCatalogStaff(locale)`: валидация, фильтрация публичных профилей, нормализация и общий кеш |
| `src/lib/contracts/catalog.ts` | Типы `CatalogStaffMember` и `CatalogStaffResponse`, без серверных импортов |
| `src/app/api/catalog/staff/route.ts` | Тонкий GET Route Handler, аналог каталога услуг |
| `src/components/sections/HomeTeam.tsx` | Отдельная секция, локальный Suspense и серверная загрузка |
| Небольшие клиентские компоненты секции | Повтор, fallback фото, сопровождение анимации при необходимости |
| `src/components/ui/Cards.tsx` | Совместимое расширение `StaffCard` для реального фото; прежние потребители сохраняют поведение |
| `src/app/[locale]/page.tsx` | Заменить только существующий блок команды на `HomeTeam`; удалить ненужную загрузку mock-сотрудников главной |
| `messages/{ru,en}.json` | Состояния секции, подписи и при необходимости утверждённые переводы по ID |
| Серверные fixtures и тесты | Синтетические ответы `book_staff`, проверки API и секции |

Минимальный DTO сотрудника:

```ts
interface CatalogStaffMember {
  id: number;
  name: string;
  specialization: string | null;
  position: string | null;
  imageUrl: string | null;
}
// Ответ: { data: { staff: CatalogStaffMember[] }, meta: { source: 'altegio', locale: 'ru' | 'en' } }
```

`id` — положительное безопасное целое, `name` — непустой текст. Некорректный обязательный элемент/форма ответа — контролируемая ошибка upstream, не успешный пустой каталог. Необязательные пустые строки превращать в `null`, позиции читать безопасно. Дубликаты ID выявлять и обрабатывать явно, не создавать повторяющиеся React keys. Возвращать только перечисленные поля: не распространять исходный объект через spread.

Не включать контакты, `user`, `user_id`, `api_id`, права, расписание, `bookable`, слоты, рейтинги и отзывы. Эти сведения не нужны карточке. Не создавать связи услуг и сотрудников дополнительными запросами на каждого человека.

`GET /api/catalog/staff?locale=ru|en`: по умолчанию `en`, неизвестные/повторные query-параметры — 400; браузер не задаёт location, токен или upstream path. Успех и ошибки имеют `Cache-Control: no-store`, безопасные коды и `Retry-After` по существующему образцу. Не возвращать upstream payload или секреты.

Server Component вызывает `getCatalogStaff(locale)` напрямую, без HTTP к собственному `/api`. Route Handler использует ту же функцию.

## 5. Кеш, загрузка и независимость секций

Кешировать только нормализованные публичные профили через существующий `cachePublicCatalog`, **14400 секунд (4 часа)**. Отдельный версионированный ключ сотрудников с location и locale, без пересечения с услугами. Не создавать таймер или отдельный Map в секции. Сохранить объединение параллельных запросов, последнюю успешную версию и существующую обработку 429. Ошибку не сохранять как пустой успешный результат.

Использовать ту же передачу локали в upstream, что у услуг (`ru-RU` / `en-US`), но не считать её гарантией перевода: спецификация `book_staff` такой гарантии не даёт. Разделение кеша по локалям обязательно, если запросы отличаются.

Главная после этапа 2 динамическая. Продолжить существующую схему: серверный компонент в локальном Suspense, при необходимости `connection()` перед загрузкой и вне `catch`. Здесь требуется четырёхчасовая ревалидация данных, а не перевод всей главной на статический ISR. Не менять глобальный режим страницы ради новой секции. Сборка без CRM должна проходить.

Ошибка или медленная загрузка команды не блокирует Hero, услуги, QuickForm и другие секции. Два источника грузятся независимо: не объединять запросы команды и услуг в общий блокирующий `Promise.all` на уровне страницы. Кеш сотрудников не содержит доступность или ближайшее время; для них в будущем нужен отдельный свежий запрос.

## 7. Состояния и анимация

- Загрузка: локальное понятное состояние/скелет без вымышленных людей.
- Пустой массив: отдельное сообщение, без карусели, intro и стрелок.
- Ошибка без кеша: локальное сообщение и повтор через `router.refresh()`, без polling и второго клиентского источника данных.
- Успех: серверный HTML/RSC содержит нормализованные карточки; браузер не обращается к Altegio API.
- При повторе сохранять фокус во время ожидания, при успехе корректно переводить его на `team-title`, если кнопка исчезла.
- Использовать механизм `data-motion-scope` и локальное подключение анимации по образцу этапа 2. Поздно пришедшие карточки видимы и корректно измеряются. Успех/ошибка команды не переинициализирует анимацию услуг побочным эффектом.

Не строить универсальный конструктор секций. Небольшое общее решение допустимо при реальном повторении, с регрессионной проверкой услуг и без переделки отложенного кеша.

## 8. Проверки и приёмка

Расширить серверный fixture-harness, а не перехватывать только браузерный `/api/catalog/staff`: серверная секция вызывает функцию напрямую. Тестовые ответы синтетические, без токенов и исходных персональных данных филиала в репозитории.

Проверить:

1. Нормализацию массива, `position` как объект/пустой массив/пустой объект, отсутствие необязательных полей; ошибочные ID/имена, форму ответа и дубли ID.
2. `bookable: false` остаётся в публичной команде; явно hidden/fired исключаются по проверенным правилам. Порядок и все опубликованные сотрудники сохраняются.
3. API RU/EN, default locale, лишние/повторные параметры, ошибки конфигурации/401/403/429/таймаут/не-JSON; безопасные ответы без сырого объекта.
4. Кеш 14400 секунд, раздельность локалей и ресурсов, общий кеш API/секции, дедупликацию, обновление устаревшего значения и сохранение последнего успешного при сбое. Отсутствие загрузки расписания и N+1.
5. Ноль/один/несколько сотрудников, длинное имя, пустую подпись, реальное фото, битый URL и стандартный аватар Altegio.
6. Загрузку, ошибку и повтор; медленную команду при успешных услугах и обратный сценарий. Отсутствие hydration warnings, правильный фокус и появление карточек при включённой анимации.
